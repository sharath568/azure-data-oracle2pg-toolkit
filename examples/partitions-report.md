## `sales.orders`

Key: ORDER_DATE DATE NOT NULL.

**Decide**

- Unique index ORDERS_PK (ORDER_ID) does not include every partitioning column (ORDER_DATE). PostgreSQL cannot enforce it across partitions: include the key (uniqueness then only holds per key value), generate the values from one sequence, or enforce it in a separate unpartitioned table.

**Behaves differently**

- Interval partitioning (every 1 month): Oracle creates partitions on insert, PostgreSQL never does. A row past the last partition fails unless partitions are created ahead of time: map-types adds a procedure, sales.orders_add_partitions, to run on a schedule (pg_cron), or use pg_partman.


## `sales.order_items`

**Decide**

- Reference partitioning (through ORDER_ITEMS_ORDER_FK) has no PostgreSQL equivalent. Either copy the parent's partition key into this table and partition it the same way (so old parents and their children can be dropped together), or leave it unpartitioned. It is created unpartitioned.


## `sales.sales_history`

**Decide**

- Unique index SALES_HISTORY_PK (SALE_ID, SALE_DATE) does not include every partitioning column (SALE_DATE, REGION_CODE). PostgreSQL cannot enforce it across partitions: include the key (uniqueness then only holds per key value), generate the values from one sequence, or enforce it in a separate unpartitioned table.


## Differences that apply to every partitioned table

- Updating the partition key moves the row to the right partition in PostgreSQL. Oracle raises ORA-14402 unless ROW MOVEMENT is enabled.
- Partition pruning needs a condition on the key column itself. `order_date >= '2024-03-01'` prunes; `date_trunc('month', order_date) = '2024-03-01'` and `order_date::date = ...` scan every partition.
- Archive old data with `ALTER TABLE ... DETACH PARTITION ... CONCURRENTLY` and `DROP TABLE`, not DELETE.
- A DEFAULT partition makes every new partition more expensive to add: PostgreSQL scans it to prove it holds no rows for the new range.
